    Lesson 1

    What an embedded system is, and why "building" its code is different

    In plain words

    An embedded system is a small computer hidden inside a product: the controller in a washing machine, a smartwatch, a car's airbag unit, a water meter. Its brain is a microcontroller: a tiny processor with a little memory (often only kilobytes) and pins that connect to sensors, LEDs and motors.

    That chip has no keyboard, no screen and no operating system you could type code into. So you write the program on your laptop, convert it into the chip's machine language, and then copy the finished program into the chip. That conversion is called the build process, and it is what this unit is about.

    Write this in the exam
    • Embedded programming is not very different from normal programming. The main change is that you must understand the target hardware, and every target platform is unique.
    • This uniqueness adds software complexity, so the developer must be more aware of the build process.
    • On a PC, build tools run on the same machine as the program and can make assumptions. In embedded work, the tools run on a host that differs from the target, so the user must give the tools explicit instructions about the target.

    Remember: write on the host, run on the target. The tools know nothing about the target unless you tell them.

    Check yourself: why can't you write code directly on a microwave's chip?

    It has no keyboard, screen, OS or development tools, and its memory is far too small to hold a compiler. Code is written and built on a host PC, then downloaded to the chip.

    Lesson 2

    Host vs target

    In plain words

    Think of a bakery. The host is the big kitchen where the cake is made: ovens, mixers, space. The target is the small lunch box the cake is delivered in. You never bake inside the lunch box.

    The host is your PC with all the tools: editor, compiler, debugger. The target is the embedded board that will run the final program. A cable (the communication link: USB, serial, JTAG or Ethernet) connects them.

    Host (development platform)Target (embedded hardware platform)
    General purpose computerSpecial purpose board
    More capable processor, more memoryLimited processor, memory and I/O
    Different I/O (keyboard, screen)Sensors, actuators, LEDs
    Capable OS (Windows / Linux)Stripped-down OS / kernel, or none
    Development tools: editor, compiler, debuggerNo development tools
    Write this in the exam
    • Software development is performed on the host using a compiler, assembler, linker, locator and debugger.
    • It produces an executable binary image that runs on the target embedded system.
    • Host and target are connected by a comm link. Draw two boxes with the table points and a double arrow labelled "comm link".

    Remember: the host is the big kitchen with every tool; the target is the small lunch box with no tools.

    Check yourself: give three differences between host and target.

    Host is general purpose while target is special purpose. Host has a powerful CPU and large memory while target is limited. Host has a full OS and development tools while target has a stripped-down kernel and no tools.

    Lesson 4

    Step 1: the preprocessor

    In plain words

    Before the compiler sees your code, a helper called the preprocessor does "copy-paste and find-replace" jobs. It only reacts to lines starting with #.

    #include "led.h"        // paste the whole contents of led.h here
#define LED_PIN 5         // replace every LED_PIN with 5
#ifdef DEBUG              // keep this block only if DEBUG is defined
    print_log();
#endif
digitalWrite(LED_PIN, 1); // compiler actually sees: digitalWrite(5, 1);
    Write this in the exam
    • Preprocessing is not part of the compiler; it is a separate step in the compilation process.
    • It runs instructions given by the programmer before the program compiles.
    • It provides: inclusion of header files, macro expansion, conditional compilation, line control.
    • Its instructions are called preprocessor directives and start with #: #include, #define, #line…

    Remember: # lines are handled by the preprocessor, before compiling. Four jobs: include, macro, conditional, line.

    Check yourself: what does the compiler see after #define MAX 10 … int a[MAX];?

    int a[10];. The macro was expanded by the preprocessor.

    Lesson 5

    Step 2: compiler, cross-compiler and assembler

    In plain words

    A processor only understands machine language: numbers called op-codes. A compiler translates C (which humans read) into op-codes. Every processor family has its own machine language, just as Tamil, Hindi and English are different languages. ARM, AVR and x86 cannot read each other's code.

    A native compiler produces code for the same kind of machine it runs on (laptop → laptop). A cross-compiler runs on your laptop but produces code for a different processor (laptop → ARM board). Embedded work almost always uses a cross-compiler, because the target can't run a compiler itself.

    An assembler does the same job for assembly language files (.s/.asm). A cross-assembler assembles for a different target.

    Native compilerCross-compiler
    Runs on platform X, makes code for XRuns on host X, makes code for target Y
    e.g. gcc on a laptop → x86 programe.g. arm-elf-gcc on a laptop → ARM program
    Write this in the exam
    • The compiler translates a human-readable language into an equivalent set of op-codes for a particular processor: source code → object file.
    • Each processor has its own machine language, so choose a compiler for your specific target processor.
    • In embedded systems the compiler almost always runs on the host, so it is a cross-compiler. The use of a cross-compiler is one of the defining features of embedded software development.
    • Example: GNU gcc and assembler as can be configured as native or cross tools. They run on common PC/Mac OSes and target AVR, Intel x86, MIPS, PowerPC, ARM and SPARC.

    Remember: cross = across machines. You build on one machine and run on another.

    Check yourself: a laptop (x86) builds code for an Arduino (AVR). Which compiler type is this?

    A cross-compiler (e.g. avr-gcc), because the code is produced for a different processor from the one the compiler runs on.

    Lesson 6

    What the compiler produces: object files and their sections

    In plain words

    Compiling one .c file gives one object file (.o). It contains machine code but is incomplete. If blink.c calls led_toggle(), which lives in led.c, then blink.o only holds a note saying "I need led_toggle, address unknown". So an object file cannot be executed.

    Inside, the compiler sorts everything into three labelled boxes called sections:

    int speed = 5;        // global WITH initial value  → .data
int count;            // global WITHOUT a value     → .bss
void blink(void) {    // the instructions of every function → .text
    count++;
}
    Write this in the exam
    • Whatever the input language, the cross-compiler's output is an object file. Parts of it contain executable code, but it cannot be executed directly.
    • It is like a large, flexible data structure, defined by a standard format such as COFF (Common Object File Format) or ELF (Executable and Linkable Format).
    • It starts with a header describing the sections that follow. In gcc: .text holds all code blocks, .data holds initialized global variables and their initial values, and .bss holds uninitialized global variables.

    Remember: Text = Tasks (code) · Data = Declared values · BSS = Blank Storage Space.

    Check yourself: which section holds int buf[100]; (global) and which holds float gain = 1.5; (global)?

    buf has no initial value, so it goes in .bss. gain has one, so it goes in .data. (Local variables inside functions live on the stack, not in these sections.)

    Lesson 7

    Step 3: the linker

    In plain words

    The linker is a jigsaw assembler. It takes every object file plus any libraries and:

    1. joins all .text pieces into one .text, all .data into one .data, all .bss into one .bss;
    2. fills in every "address unknown" note by matching names. blink.o needs led_toggle, and led.o provides it. This is called resolving symbols.

    The result is a relocatable program: complete, but no real memory addresses have been chosen yet. It is like a book that is fully written but whose pages aren't numbered. If a name can't be found, you get the familiar error undefined reference to 'led_toggle'. That error comes from the linker.

    Write this in the exam
    • All object files from compilation must be combined. Individually they are incomplete: some variable and function references are unresolved.
    • The linker combines them and resolves all unresolved symbols.
    • By merging the text, data and bss sections of the inputs, it creates one new object file containing all code and data.
    • The output is a special "relocatable" copy of the program: complete except that no memory addresses have been assigned to its sections.

    Remember: the linker resolves symbols; the locator assigns addresses.

    Check yourself: what does "relocatable" mean?

    The program is complete (all symbols resolved, sections merged), but its code and data can still be placed anywhere in memory, because no physical addresses have been assigned yet.

    Lesson 8

    Step 4: the locator and the linker script

    In plain words

    Every board has memory at fixed addresses. On one board, flash ROM might start at 0x60000000 and RAM at 0x00400000. The locator gives every section its exact "house number" in that memory. It can't guess the board's layout, so you hand it a map called the linker script. The output is the executable binary image (.exe / .hex / .bin), which is ready to burn into the chip.

    In GNU tools there is no separate locator program. Locating is built into the linker ld, and you pass it the linker script.

    ENTRY (main)                                   /* first instruction to run      */
MEMORY {
  ram : ORIGIN = 0x00400000, LENGTH = 64M      /* 64 MB RAM starts here         */
  rom : ORIGIN = 0x60000000, LENGTH = 16M      /* 16 MB flash ROM starts here   */
}
SECTIONS {
  data : { _DataStart = . ; *(.data) _DataEnd = . ; } >ram   /* initialized data */
  bss  : { _BssStart  = . ; *(.bss)  _BssEnd  = . ; } >ram   /* uninitialized    */
  text : { *(.text) } >ram                                   /* instructions     */
}
    LineMeaning
    ENTRY(main)The first executable instruction; the entry point is main.
    MEMORYTells the locator the board has 64 MB RAM and 16 MB flash ROM, with their start addresses.
    SECTIONS … >ramPlace data, bss and text in RAM starting at 0x00400000.
    _DataStart, _DataEndNames starting with _ can be used like variables in C. Startup code uses them as start/stop addresses to copy the initial values of initialized variables from ROM into RAM.
    Write this in the exam
    • The locator converts the relocatable program into an executable binary image.
    • You provide information about the target board's memory. The locator uses it to assign physical memory addresses to each code and data section.
    • The output is a binary image with physical addresses that can be downloaded or programmed into a memory chip.
    • In GNU tools the locator is built into the linker (ld), and the memory information is passed as a linker script.

    Remember: linker script = the map of the board you give the locator.

    Check yourself: which tool assigns physical addresses, and which file tells it the memory layout?

    The locator (inside GNU ld) assigns them, using the linker script (e.g. viperlite.ld).

    Lesson 9

    The map file: the linker's report card

    In plain words

    After linking and locating, the linker can write a map file that says where everything ended up and how big it is. The linker script is the plan you wrote; the map file is the result the linker reports back.

    Memory Configuration
Name        Origin               Length               Attributes
FLASH       0x0000000000001000   0x00000000000ff000   xr
RAM         0x0000000020000008   0x000000000003fff8   xrw

    Attributes: x = executable, r = readable, w = writable. Flash is xr (code can run from it but not be written at run time); RAM is xrw.

    Write this in the exam
    • The .map file gives a complete listing of all code and data addresses in the final image.
    • Its information resembles the linker script, but it holds results rather than instructions: actual section lengths and the names and locations of public symbols.
    • It is a symbol table for the whole program, useful to understand and optimize memory. It shows memory regions with location, size and access rights.

    Remember: linker script = plan (input) · map file = report (output).

    Check yourself: your firmware no longer fits in flash. Which file shows which section is too big?

    The map file. It lists every section's size and address.

    Lesson 10

    Real commands: building the Blinking LED program

    In plain words

    The slides build a "Blinking LED" program for the Arcom VIPER-Lite board. It has two source files, led.c and blink.c. Commands are typed in a shell (Cygwin bash on Windows, a normal terminal on Linux). First compile each file, then link + locate in one command.

    # 1. compile (general form: arm-elf-gcc [options] file ...)
arm-elf-gcc -g -c -Wall -I../include led.c      # → led.o
arm-elf-gcc -g -c -Wall -I../include blink.c    # → blink.o

# 2. link + locate (general form: arm-elf-ld [options] file ...)
arm-elf-ld -Map blink.map -T viperlite.ld -N -o blink.exe led.o blink.o
# → blink.exe (binary image) and blink.map (map file)

    Check yourself: why is -c needed in the gcc commands?

    Without -c, gcc would also try to link. Here we only want object files, because linking and locating are done separately by arm-elf-ld with the linker script.

    Lesson 11

    After building: download, test, fix, repeat

    In plain words

    The binary image must now be copied into the target's memory (Unit 2 covers how). Then the target is reset and runs it. It rarely works first time, so you loop: build → download & debug → fix bugs → build again. This loop is the Edit–Test–Debug cycle, the implementation phase of development.

    In the development phase, hardware and software are developed in parallel. Hardware: select it, assemble the target system, test it. Software: develop using edit-test-debug cycles until test results are OK. The code is burnt into the hardware with a device programmer and tested. If a test fails, reassemble on hardware errors or redesign on software errors.

    Write this in the exam

    Approaches during the edit-test-debug cycle: using a target system · using an emulator for the target · using the target processor + ICE · using a simulator for the hardware · using an IDE or prototyping tool.

    Software tools for embedded development: SDK, source-code engineering software, RTOS, IDE, emulator, editor, interpreter, compiler, assembler, cross assembler, locator, testing & debugging tools.

    Remember: build → download → test → fix → build… until the result is OK.

    Check yourself: name three approaches used during the edit-test-debug cycle.

    Any three of: a target system, an emulator, the target processor with ICE, a hardware simulator, an IDE/prototyping tool.

    Lesson 12

    Interpreter vs compiler + assembler (asked in Paper D)

    In plain words

    An interpreter is like a live translator at a meeting. It reads your program one line at a time, every time it runs, and executes it (e.g. MicroPython on a board). You change code and run it instantly, which is great for trying ideas. But it is slow, and the interpreter itself takes up the chip's memory.

    A compiler + assembler translates the whole program once, before it runs, into machine code. The chip then runs that code directly, which is fast and small. The cost is the full build cycle (compile, link, locate, download) after every change.

    AspectInterpreterCompiler + assembler
    When translatedLine by line, at run timeWhole program, ahead of time
    SpeedSlowFast (native op-codes)
    MemoryInterpreter + source stored on chipOnly the compact binary
    DevelopmentInstant edit-and-runBuild cycle after every change
    Timing / powerUnpredictable, more powerDeterministic, less power
    ErrorsFound only when that line runsMany caught at compile time
    Best forPrototypingProduction

    Remember: interpret while prototyping, compile for production.

    Check yourself: why does a battery-powered water meter ship compiled code?

    Compiled code is faster, smaller and deterministic, and it uses fewer CPU cycles, so the battery lasts longer. It also fits a tiny MCU with no room for an interpreter.

    (a) Build steps 5 M

    Draw Fig 1.1 with the file names changed. Then write:

    Runs on platform X, produces code for XRuns on host X, produces code for target Y

    (c) Linker script and map file 3 M

    Scenario 1.210 marksK3

    A glucose monitor firmware builds with no errors, but on power-up the global variable int threshold = 180; reads as garbage, while int count; is fine. (a) Explain the object-file sections and which one each variable lives in. 3 M (b) Explain relocatable vs executable image and the role of the locator in this bug. 4 M (c) Write the GNU commands with options to compile sensor.c, app.c and link-locate them using gluco.ld. 3 M

    Solution

    (a) Sections 3 M

    • .text: machine code of all functions.
    • .data: initialized globals and their initial values → threshold = 180 lives here.
    • .bss: uninitialized globals → count lives here (zeroed at startup).

    (b) Relocatable → executable, and the bug 4 M

    • The linker output is relocatable: all code/data merged and symbols resolved, but no physical addresses.
    • The locator reads the memory map (linker script) and assigns physical addresses, producing the executable binary image.
    • On an embedded board, .data runs from RAM, but its initial values must be stored in non-volatile ROM (RAM is blank at power-up). Startup code must copy them from ROM to the RAM range _DataStart…_DataEnd defined in the linker script.
    • Cause: the linker script did not define the load address / _DataStart, _DataEnd symbols correctly, or startup code never copied .data. So threshold holds random RAM contents. count is fine because .bss only needs zeroing.
    • Fix: correct the SECTIONS entry for .data (RAM run address, ROM load address), and check the addresses in the map file.

      Lesson 1

      What "loading" or "downloading" the program means

      In plain words

      At the end of Unit 1 you have a file on your laptop: the executable binary image, often called hex code. The chip can't run it from your laptop. It must be written into the chip's own non-volatile memory (flash / ROM), which keeps the program even when power is off.

      Writing it in is called programming, burning, flashing or downloading. There are exactly two ways in the syllabus:

      1. Device programmer: take the chip out, program it in a separate machine, put it back.
      2. In-system programming (ISP): program the chip while it stays on the board.

      Remember: the hex code goes into target flash/ROM, either off-board (device programmer) or on-board (ISP).

      Check yourself: why must the program go into flash/ROM rather than RAM?

      RAM loses its contents when power is removed. Flash/ROM is non-volatile, so the program is still there at the next power-on.

      Lesson 2

      Method 1: the device programmer

      In plain words

      A device programmer is a separate box with a socket on top, usually a ZIF socket ("zero insertion force": a lever clamps the chip without pressing). It works like burning a CD in a separate writer and then putting the CD in the player. You remove the chip from the board, put it in the socket, burn the program, and fit the chip back on the board.

      Write this in the exam: 4 steps
      1. Once the binary image is ready on the computer, connect the device programmer to the computer.
      2. Place the µP/µC or memory chip (usually the ROM that will hold the image) in the proper socket on the programmer.
      3. In the programmer's software interface, select the target µP/µC the image is for.
      4. The device programmer transfers the binary image to the chip bit by bit.

      Diagram: Host computer → Device programmer → µP/µC/memory chip.

      Remember: Cats Prefer Sunny Terraces = Connect, Place, Select, Transfer.

      Check yourself: what is the main inconvenience of a device programmer during development?

      The chip has to be removed from the board and re-inserted every time the code changes. That is slow, can bend pins, and is impossible for soldered SMD chips.

      Lesson 3

      Method 2: in-system programming (ISP / ICSP)

      In plain words

      With ISP the chip never leaves the board. The board has a small programming header (a few pins). You plug a programmer cable into it, e.g. a PICkit 3 for PIC chips or the ICSP header on an Arduino, and the laptop sends the program straight into the chip. It is like updating your phone's software while the phone stays in your hand.

      Write this in the exam
      • Some target platforms use a piece of hardware called an ISP that has a hardware interface to both the computer and the target board's chip.
      • ISP, also called in-circuit serial programming (ICSP), is the ability to program the processor/controller while it is installed in the complete system, instead of programming the chip before installing it.
      • It lets firmware updates reach on-chip memory without special programming circuitry on the board, and it simplifies design work.
      • The user sends the image through the ISP's software interface. This avoids repeatedly removing the µP/µC or ROM, which a device programmer would need.

      Remember: ISP = In the System, so the chip stays soldered.

      Check yourself: what does the board need so ISP can work?

      A programming header/connector (ICSP, JTAG or SPI pins) wired to the chip, so the ISP hardware can connect to it while it stays on the board.

      Updating a device that is already installed far away

      In plain words

      What if the meter is already fixed on a wall somewhere in the city? Nobody can pull out the chip or plug in a cable. The answer is a bootloader: a small program kept in a protected part of flash. When a new version arrives over the device's network link (GSM, NB-IoT, LoRa, Wi-Fi), the bootloader writes it into the application area of flash and restarts. This is called OTA (over-the-air) update or in-application programming. It is in-system programming done remotely.

      Write this in the exam
      • Choose in-system reprogramming via a bootloader (OTA). A device programmer is impossible because the chip is sealed inside an installed device.
      • No technician visit and no chip removal. Every deployed device can be updated at once.
      • Safety: verify the image with a checksum/CRC, keep a backup image for rollback, and use signed images.

      The slides don't cover OTA. Say "ISP extended remotely using a bootloader" to connect it to the syllabus.

      Remember: remote update = bootloader + comm link = OTA.

      Check yourself: what stops a bad OTA update from "bricking" the device?

      The bootloader is never overwritten. It checks the CRC/signature before switching to the new image and can roll back to the backup image.

      Lesson 6

      Why embedded debugging needs special tools

      In plain words

      On a laptop you add printf or press "Debug" to pause the program and look at variables. An embedded board has no screen, and the program runs on a different computer from your debugger. Some bugs happen before main(), or only on the real wires. So there is a family of tools, from cheapest and least real to most expensive and most real:

      1. Simulator: pretend CPU on the laptop
      2. Remote debugger: laptop controls the real CPU over a cable
      3. In-circuit emulator (ICE): special hardware replaces the CPU
      4. Plus the logic analyzer, which watches the digital signals on the wires

      Remember: S → R → I: each step costs more and gets closer to the real hardware.

      Check yourself: order the three debugging tools by cost.

      Simulator (cheapest) → remote debugger → ICE (most expensive).

      Lesson 7

      Simulator

      In plain words

      A simulator is a program on your laptop that pretends to be the target processor, the way a flight simulator pretends to be a plane. It runs your machine code instruction by instruction and shows the registers and memory. You don't even need the board. But it only imitates the processor, not the timers, ADC, UART or sensors around it, and it runs much slower than the real chip.

      Write this in the exam
      • A host-based program that simulates the functionality and instruction set of the target processor.
      • Its front-end has text or GUI windows for source code, register contents, etc.
      • Valuable during early stages of development; the lowest-cost development environment.
      • Disadvantages: simulates only the processor, not the peripherals. Many real-time systems are hard to debug with simulation alone. It runs 100–1000× slower than the real processor, so long timeout delays must be removed when simulating.

      Remember: a simulator is software on the host: cheap, early, CPU only, slow.

      Check yourself: why might a UART bug never appear in a simulator?

      The simulator does not model peripherals such as the UART or its timing, so hardware-interaction bugs stay hidden.

      Lesson 8

      Remote debugger

      In plain words

      A remote debugger is a normal debugger split into two halves. The front-end is the window on your laptop where you click "step" or "set breakpoint". The back-end is a tiny helper program (a debug monitor) running on the target, which obeys those commands. The two halves talk over a cable. So the debugger and the program being debugged run on two different computers.

      The catch: the back-end is itself software on the target, so it must already be running. That means you can't debug the startup code that runs before it. Software breakpoints work by temporarily overwriting instructions, which is only possible in RAM, so code must run from RAM.

      Write this in the exam
      • One of the most common tools to download, execute and debug embedded software over a communication link.
      • The front-end (host) GUI shows the source, current register contents and other information. The back-end runs on the target, gives low-level control of the processor, and talks to the front-end over the link.
      • Features: start/restart/kill, stepping through the program, software breakpoints, reading/writing registers or data at an address.
      • Disadvantages: can't debug startup code, code must execute from RAM, needs a target processor to run the final software.

      Remember: remote debugger = front-end + back-end over a link. It can't see startup code.

      Check yourself: why can't a remote debugger debug code that runs straight after reset?

      Its back-end (debug monitor) must start on the target first. Code that runs before it, such as startup code, is out of its reach.

      Lesson 9

      In-circuit emulator (ICE)

      In plain words

      "Emulate" means imitate exactly. With an ICE you remove the real processor from the board and plug in a probe connected to the ICE box. The box contains its own copy of the processor plus memory and software, and behaves exactly like the CPU, while letting you watch and freeze everything from the very first instruction. It is the most powerful option and the most expensive.

      Write this in the exam
      • An emulator is hardware/software that lets one computer system run programs written for another.
      • An ICE takes the place of the target processor. It contains a copy of the target processor plus RAM, ROM and its own embedded software.
      • It provides everything a remote debugger does, plus debugging of startup code and programs running from ROM.
      • It lets you examine the processor state while the program runs, using the remote debugger as the human interface.
      • Flexible: many applications can be developed on one system instead of testing multiple targets. Disadvantage: expensive.

      Diagram: PC ⇄ (TX/RX, RS232) ⇄ ICE box [COM port + target system emulating circuit] ⇄ cable ⇄ MCU socket.

      Remember: ICE replaces the CPU, sees everything including startup and ROM code, and costs the most.

      Check yourself: a crash happens 2 ms after power-on, before main(). Which tool do you use?

      An ICE, because it is the only one of the three that can debug startup code running from ROM on the real hardware.

      Logic analyzer: what it is and how it works

      In plain words

      Sometimes the code is right but the wires misbehave: an I²C bit arrives late, a glitch flips a signal. A logic analyzer clips probes onto many digital lines (usually more than 8) of the System Under Test (SUT), records them as 1s and 0s over time, and shows them as waveforms. An oscilloscope shows exact voltages on 2–4 channels; a logic analyzer shows logic levels on many channels.

      How a sample becomes 0 or 1: at every clock tick it compares the voltage with a threshold. Example with a 1.4 V threshold: 3.1 V → 1, 0.2 V → 0. Each result is stored in one memory location, and the stored pattern is drawn on the screen.

      Write this in the exam
      • Definition: an instrument for troubleshooting digital systems. It captures the data of a digital system and displays it for analysis.
      • Components: probes, internal clock generator, threshold generator, comparator, memory, trigger block.
      • Probes connect the SUT's data lines. The internal clock generator makes sampling pulses. The comparator compares samples with the threshold voltage from the threshold generator. The memory stores the captured data.
      • Working: sample the input at each clock pulse → compare with the threshold → above = logic 1, below = logic 0 → the series of 0s and 1s is stored, one sample per memory location → displayed.

      Remember: Pretty Intelligent Tools Capture My Timing = Probes, Internal clock, Threshold, Comparator, Memory, Trigger.

      Check yourself: threshold is 1.5 V and samples are 3.0, 0.4, 2.2, 1.1 V. What is stored?

      1, 0, 1, 0.

      Two modes: timing (asynchronous) and state (synchronous)

      In plain words

      The only question is who decides when to take a sample. In timing mode the analyzer uses its own internal clock, ticking fast and regularly, so you see the true shape and timing of signals, including glitches. In state mode it samples only when the circuit's own clock ticks, so you see the actual data value on each clock edge, e.g. the byte on a bus.

      Modern analyzers combine both. The signal enters through the probe buffer, is clocked into a latch, stored in memory and displayed by the µP. The latch clock is internal (async) or external (sync).

      Applications: signal troubleshooting, communication protocol debugging, timing anomaly detection, execution flow visualization, software–hardware interaction analysis, comprehensive testing, data integrity evaluation, validation of complex algorithms.

      Remember: Timing uses the Internal clock (async); State uses the SUT clock (sync).

      Check yourself: you want to catch a 50 ns glitch between clock edges. Which mode?

      Timing (asynchronous) mode with a fast internal clock. State mode only samples on SUT clock edges and would miss it.

        Lesson 1

        What code optimization is, and why embedded systems care

        In plain words

        Optimization means getting the same result with less work. If a loop runs 1000 times and computes 5 * 4 every time, you are doing the same multiplication 1000 times for nothing. Write 20 once instead: same answer, less work.

        On a laptop this barely matters. On a small microcontroller every instruction costs time, battery and memory, all of which are scarce. So embedded code is optimized to run faster, fit in less flash/RAM, and save power.

        Write this in the exam
        • Optimization is modifying a system so some aspect works more efficiently or uses fewer resources: runs faster, uses less memory, or draws less power.
        • It is a program transformation technique that improves code to consume fewer resources (CPU, memory) and deliver high speed. High-level constructs are replaced by efficient low-level code.
        • It is usually done at the end of development, because it reduces readability and adds code only for performance.
        • Features of optimized code: executes faster · smaller code size · efficient memory use · better performance · reduced time and space complexity.

        Remember: same output, fewer cycles, less memory, less power.

        Check yourself: why is optimization usually done at the end of development?

        Optimized code is harder to read and maintain, so you first make the program correct, then optimize it.

        Lesson 2

        The rules every optimization must follow

        In plain words

        An optimization is only allowed if the program still gives exactly the same answers. Making code fast but wrong is not optimization; it is a bug. Example of an illegal change: replacing x / 2 with x >> 1 when x can be negative, since −3/2 = −1 but −3>>1 = −2 on most machines.

        Write this in the exam: criteria
        1. It must preserve the meaning of the program: it cannot change the output for any input, and it cannot introduce an error.
        2. It should, on average, speed up programs.
        3. It should itself be fast and not delay the overall compiling process.

        Remember: meaning first, speed second, and a fast optimizer.

        Check yourself: which criterion is broken if an "optimization" changes a result for some inputs?

        Criterion 1, "preserve the meaning of the program".

        Lesson 3

        Where optimization happens

        In plain words

        Inside a compiler, the front-end reads your code and checks errors, the code optimizer improves an intermediate form of it, and the code generator produces machine code. Some improvements work on any processor (machine-independent). Others use tricks specific to one processor, such as a special instruction (machine-dependent).

        Write this in the exam
        • Machine-independent: improves target code without considering properties of the target machine.
        • Machine-dependent: improves target code by checking properties of the target machine (registers, special instructions).
        • Levels: (1) Design level: use resources well by choosing efficient algorithms and writing good-quality code. (2) Compile level: an optimizing compiler optimizes as much as it can predict.
        • Phases: Source code: algorithm changes give spectacular gains. Intermediate code: the compiler improves loops, procedure calls and address calculations (only optimizing compilers do this). Target code: the compiler uses registers efficiently.

        Remember: independent = works on any CPU · dependent = uses this CPU's tricks.

        Check yourself: is replacing ADD #1,R with INC R machine-dependent or independent?

        Machine-dependent. It relies on the target having an INC instruction.

        Lesson 4

        Basic blocks and the four types of optimization

        In plain words

        A basic block is a run of statements with no jumps in or out in the middle: control enters at the top and leaves at the bottom. The four types differ only in how much code they look at, like editing an essay:

        • Local: fix one sentence (one basic block).
        • Global: fix across paragraphs (many blocks in a function).
        • Loop: fix the chorus that repeats (the loop body runs many times, so gains multiply).
        • Peephole: use a magnifying glass on 2–3 machine instructions at a time.
        Write this in the exam
        1. Local optimization: applies to a basic block in isolation. It is the simplest form and doesn't analyse the whole procedure. Techniques: constant folding, constant propagation, algebraic simplification, operator strength reduction, dead code elimination (+ CSE).
        2. Global optimization: across basic blocks within a procedure/function. It uses data-flow analysis; each basic block is a node in the program's flow graph, and it can extend to the whole control-flow graph.
        3. Loop optimization: applied on loops (loop invariants, induction variables).
        4. Peephole optimization: applies across boundaries on a small window of instructions.

        Remember: Little Girls Love Peaches = Local, Global, Loop, Peephole.

        Check yourself: which type needs data-flow analysis?

        Global optimization, because it works across basic blocks.

        Lesson 5

        Technique: constant folding

        In plain words

        If an expression contains only constants, work out the answer while compiling, so the chip never has to.

        // before                          // after
circ = (22.0/7) * dia;             circ = 3.14 * dia;
k = 60 * 1000 / 4;                 k = 15000;
        Write this in the exam

        Constant folding evaluates expressions whose operands are constant at compile time. Example: circumference = (22/7) × diameter; (22/7) is replaced with 3.14 at compile time, saving execution time.

        Remember: fold = do the constant maths before running.

        Check yourself: fold int s = 2 * 8 + 1;

        int s = 17;

        Lesson 6

        Technique: constant propagation

        In plain words

        If a variable was given a constant value and isn't changed afterwards, replace later uses of the variable with that value. This often creates new chances for folding.

        // before                          // after propagation + folding
pi = 3.14;  r = 10;
area = pi * r * r;                 area = 314;
        Write this in the exam

        If a variable is assigned a constant, the compiler replaces the variable with that constant wherever it is used later, provided its value does not change in between. Example: pi = 3.14, radius = 10; area = pi × radius × radius. Constants are substituted at compile time, saving execution time.

        Remember: propagate = spread the known value forward.

        Check yourself: x = 4; y = x + 1; x = 9; z = x * 2; What can be propagated into y and z?

        y = 4 + 1 = 5. z uses the new value, 9 × 2 = 18. Propagation must use the latest value.

        Lesson 7

        Technique: algebraic simplification

        In plain words

        Use school algebra rules to delete useless work: adding 0, multiplying by 1, subtracting a thing from itself.

        // before               // after
a[0] = i + 0;           a[0] = i;
a[1] = i * 0;           a[1] = 0;
a[2] = i - i;           a[2] = 0;
a[3] = 1 + i + 1;       a[3] = 2 + i;
b    = -(-i);           b    = i;
        Write this in the exam

        Use algebraic properties to simplify expressions: replace an expression with an equivalent, more efficient one. Identities: x+0 = x, x×1 = x, x×0 = 0, x−x = 0, −(−x) = x.

        Remember: +0, ×1, x−x and −(−x) can all be simplified away.

        Check yourself: simplify sum = sum + (x*1) + (c*d) - (c*d);

        sum = sum + x; since x×1 = x and +(c×d)−(c×d) = 0.

        Lesson 8

        Technique: strength reduction

        In plain words

        Some operations are "strong" (expensive) and some "weak" (cheap). On a small microcontroller an add takes about 1 cycle, a multiply takes several, and a divide can take tens of cycles (many MCUs have no hardware divider). So replace expensive operators with cheaper ones that give the same result.

        B = A * 2;    →   B = A + A;      // or A << 1
y = x * 8;    →   y = x << 3;     // shift left 3 = multiply by 8
p = x * x;    ←   (keep: pow(x,2) → x*x is also strength reduction)
        Write this in the exam

        Strength reduction replaces expensive, costly operators with simple, cheaper ones. Example: B = A × 2 → B = A + A, because multiplication costs more than addition.

        Remember: ÷ → ×, × → + or <<. Swap the strong operator for a weaker one.

        Check yourself: reduce t = i * 16; for unsigned i.

        t = i << 4; (inside a loop, even better is t = t + 16; each iteration; see Lesson 12).

        Lesson 9

        Technique: dead code elimination

        In plain words

        "Dead" code is code that never runs, can't be reached, or computes a result nobody ever uses. Deleting it saves flash space and time.

        // before                         // after
i = 0;                            i = 0;
if (i == 1) { a = x + 5; }        // i is always 0, so the if-block can never run

int z = (a + b) - (a + b);        // z is never used later, so delete the line
        Write this in the exam

        Dead code elimination removes code that either never executes, is unreachable, or whose output is never used even if it executes.

        Remember: never runs, unreachable, or unused result means delete it.

        Check yourself: with #define DEBUG 0, what happens to if (DEBUG) printf(...);?

        The condition is always false, so the whole statement is dead code and is removed.

        Lesson 10

        Technique: common sub-expression elimination (CSE)

        In plain words

        If the same expression is computed twice and its inputs haven't changed, compute it once and reuse the answer.

        // before                          // after
S1 = 4 * i;                        S1 = 4 * i;
S2 = a[S1];                        S2 = a[S1];
S3 = 4 * j;                        S3 = 4 * j;
S4 = 4 * i;   // redundant         S5 = n;
S5 = n;                            S6 = b[S1] + S5;
S6 = b[S4] + S5;
        Write this in the exam

        CSE eliminates redundant expressions and avoids computing them again and again. In the example, S4 = 4×i repeats S1, so S4 is removed and b[S4] becomes b[S1].

        Remember: same expression, same inputs: compute once, reuse.

        Check yourself: apply CSE to x = (a+b)*c; y = (a+b)*d;

        t = a + b; x = t * c; y = t * d;

        Lesson 11

        Loop optimization 1: code motion (moving loop-invariant code out)

        In plain words

        Anything inside a loop that gives the same result every iteration is "loop-invariant". Compute it once, before the loop. The loop runs n times, so you save n−1 computations.

        // before                          // after (code motion)
i = 1; s = 0;                      i = 1; s = 0;
do {                               a = 5;
    s = s + i;                     do {
    a = 5;        // same always       s = s + i;
    i = i + 1;                         i = i + 1;
} while (i <= n);                  } while (i <= n);
        Write this in the exam

        Loop optimization improves performance by reducing the overheads of executing loops, by removing loop invariants and induction variables. Moving a = 5 outside the do-while loop is called code motion.

        Remember: if it doesn't change inside the loop, move it out.

        Check yourself: in for(i=0;i<n;i++){ x = 5*4; sum += x + i; }, what moves out?

        x = 20; (folded as well) goes before the loop; the body becomes sum += x + i;.

        Lesson 12

        Loop optimization 2: induction variables

        In plain words

        An induction variable changes by a fixed step each time round the loop. If t1 = i * 4 and i goes up by 1, then t1 simply goes up by 4. So stop multiplying and just add 4 each time. The multiply becomes an add (strength reduction), and t1 no longer depends on i.

        // before                          // after
while (i <= n) {                   t1 = 0;   // i starts at 1: first t1+4 = 4 = 1*4
    s  = s + a[i];                 while (i <= n) {
    t1 = i * 4;                        s  = s + a[i];
    s  = s + b[t1];                    t1 = t1 + 4;       // "+" replaced "*"
    t2 = t1 + 2;                       s  = s + b[t1];
    s2 = s2 + c[t2];                   s2 = s2 + c[t1 + 2];
    i  = i + 1;                        i  = i + 1;
}                                  }
        Write this in the exam

        t1 and t2 are induction variables: i induces t1, and t1 induces t2. "+" replaced "×", and t1 became independent of i.

        Remember: a variable that moves in fixed steps can use + instead of ×.

        Check yourself: in for(i=0;i<n;i++){ y = i*16; sum += y/2; }, what is the induction-variable rewrite?

        y/2 = i×8, so keep t = 0; before the loop, write sum += t; t += 8; in the body, and remove the multiply and divide.

        Lesson 13

        Peephole optimization

        In plain words

        Imagine sliding a small window, the peephole, over the generated machine code, 2–3 instructions at a time. Whenever the window shows something wasteful, replace it with something shorter or faster. Because it looks at real machine instructions, it is machine-dependent.

        MOV R0, a   ;  STORE a, R0     → drop the store (a already holds R0)   redundant load/store
JMP L1 ... L1: JMP L2          → JMP L2                               flow of control
JMP L3 ; MOV R5,#0 (no label)  → delete MOV                           unreachable code
MUL R3, #8                     → LSL R3, #3                           strength reduction
ADD R2, #1                     → INC R2                               machine idiom
        Write this in the exam
        • A technique that operates on one or a few instructions at a time and performs machine-dependent improvements.
        • It peeps into a single instruction or a sequence of 2–3 instructions (the peephole) and replaces it with the most efficient alternative. The peephole is a small moving window on the target code.
        • Characteristics: redundant-instruction (load/store) elimination · flow-of-control optimization (removing multiple jumps) · elimination of unreachable code · algebraic simplification · reducing operator strength · use of machine idioms (replace Add #1,R with Inc R).

        Remember: Really Fast Unicorns Always Sprint Miles = Redundant, Flow, Unreachable, Algebraic, Strength, Machine idioms.

        Check yourself: which characteristic turns JMP L1 + L1: JMP L2 into JMP L2?

        Flow-of-control optimization (eliminating jumps to jumps).

        Lesson 14

        Embedded extras, and a method for any optimization question

        In plain words

        For "resource-constrained embedded system" questions, add these to the textbook techniques:

        • Loop unrolling: do 4 items per iteration, so there are 4× fewer loop checks.
        • Pointer increment (*p++) instead of recomputing a[i]'s address.
        • Count-down loops (n != 0): comparing with zero is cheaper.
        • Right data types: uint8_t/int16_t for small values, a wider accumulator (int32_t) to avoid overflow.
        • Hoist a constant multiplier out of a sum: Σ(2·x) = 2·Σx.
        Method: 6 questions to ask on every line
        1. Only constants? → fold
        2. A variable with a known constant value? → propagate
        3. +0, ×1, x−x, +E−E? → simplify
        4. Same expression twice? → CSE
        5. Result never used / never runs? → dead code
        6. Inside a loop: same every time? → move out. Grows by a fixed step? → induction variable (× → +)

        Then write the clean code, a before/after operation count table, and a line that the output is unchanged.

        Remember: annotate every line, rewrite, count operations, state that the output is the same.

        Check yourself: which 3 techniques fix for(i=0;i<1000;i++) sum = sum + d[i]*2;?

        Hoist the ×2 out (algebraic simplification / code motion), loop unrolling, and a pointer instead of index (induction variable). Also use a wide accumulator.

        An embedded system in a wearable health monitoring device continuously reads sensor data and processes it to display results:

        int sum = 0;

    sum = sum + sensorData[i] * 2;
}

        Identify the possible inefficiencies when used in a resource-constrained embedded system, suggest an optimized version, and explain why it is more efficient.

        Solution

        Inefficiencies 4 M

        1. Repeated multiplication: * 2 is done 1000 times. By the distributive law, Σ(2·x) = 2·Σx, so it can be done once.
        2. Loop overhead: 1000 compare + branch + increment operations.
        3. Index address calculation: sensorData[i] recomputes base + i×size every time (an induction variable).
        4. Overflow risk: 1000 samples × 2 × (e.g. 4095 from a 12-bit ADC) ≈ 8.2 M, which overflows a 16-bit int on 8/16-bit MCUs. Wrong result = wasted work.
        5. Counting up needs a compare against 1000; counting down to 0 uses the CPU's zero flag.

        Optimized code 4 M

        int32_t sum = 0;                         // wide accumulator: no overflow
const int16_t *p = sensorData;           // pointer instead of index (induction variable)
for (uint16_t n = 250; n != 0; n--) {    // count-down loop, unrolled ×4 (1000 / 4 = 250)
    sum += p[0] + p[1] + p[2] + p[3];
    p += 4;
}
sum = sum * 2;                           // multiply hoisted out: 1 op instead of 1000
                                         // (compiler emits a single shift)

        Why it is more efficient 2 M

        OperationOriginalOptimized
        Multiplications10001
        Loop compare + branch1000250
        Index calculations10000 (pointer add every 4)

        Fewer CPU cycles per sample means the MCU sleeps sooner, which extends battery life (critical for a wearable). The result is identical and now overflow-safe. Techniques: algebraic simplification / code motion, strength reduction, loop unrolling, induction variable (pointer), data-type selection.

          1Learn it, step by step

          Lesson 1

          Why model a program as a graph?

          In plain words

          Code is text, which makes it hard to "see" which calculation depends on which, or which way the program can branch. A graph (boxes and arrows) turns the code into a picture, like a metro map of your program. Compilers and designers use these pictures to reorder operations, plan hardware, and spot parallel work.

          There are two pictures in this unit:

          • DFG (Data Flow Graph): shows how data flows through calculations. Used for code with no if/loops.
          • CDFG (Control Data Flow Graph): shows decisions and loops (control) plus the data work inside each part.
          Write this in the exam

          Programs in embedded systems are modelled for analysis. A program has basic blocks, conditional statements, etc. It can be represented by a Data Flow Graph (DFG) and a Control Data Flow Graph (CDFG).

          Remember: DFG = data only (no decisions) · CDFG = decisions + data.

          Check yourself: code has an if-else. DFG or CDFG?

          A CDFG. A DFG can't represent conditionals.

          Lesson 2

          Basic blocks: how to find them in code

          In plain words

          A basic block is a group of statements that always run together, top to bottom: one way in, one way out, no branch in the middle. To split code into blocks, start a new block:

          1. at the first statement,
          2. at any statement that a branch/loop can jump to,
          3. right after any if / loop condition / return.
          int result = 0;              // B1 starts (first statement)
if (x > 0) {                 // decision, which ends B1
    result = x * 2;          // B2 (target of the T branch)
    count++;                 //    still B2: runs together with the line above
} else {
    result = -1;             // B3 (target of the F branch)
}
return result;               // B4 (the paths join here)
          Write this in the exam

          A basic block has one entry and one exit point, with no conditionals inside. A DFG models one basic block; a CDFG connects many basic blocks through decision nodes.

          Remember: a new block starts at the first line, at every jump target, and after every decision.

          Check yourself: how many basic blocks does a=1; b=2; c=a+b; have?

          One. There are no branches, so all three statements run together.

          Lesson 3

          Single assignment form: give every value its own name

          In plain words

          In normal code a variable can be overwritten: x = a - c; then later x = a + c;. In a graph that is confusing, because which "x" does an arrow mean? So before drawing a DFG we rename: the first x becomes x1, the second x2. Every later use points to the most recent version. Now each name is assigned exactly once.

          // original            // single assignment form
w = a + b;             w  = a + b;
x = a - c;             x1 = a - c;
y = x + d;             y  = x1 + d;     // uses the x that exists at this point → x1
x = a + c;             x2 = a + c;      // second assignment → new name
z = y + e;             z  = y + e;
          Write this in the exam
          • Before drawing a DFG, represent the program in single assignment form: each variable on the left side appears only once.
          • It verifies there is no cyclic form in the statements and identifies a unique location for each variable.
          • Repeated assignments to a variable are rewritten with new names, and later uses refer to the latest assigned version.

          Remember: assign once, rename the rest, and always use the latest name.

          Check yourself: convert a = b + c; a = a * 2; d = a + 1;

          a1 = b + c; a2 = a1 * 2; d = a2 + 1;

          Lesson 4

          Drawing a DFG step by step

          In plain words

          A DFG has just two shapes. Squares are values (variables, inputs, results). Circles are operators (+, −, ×, …). Arrows show "this value is used by that operator" and "this operator produces that value". Steps:

          1. Draw the input variables as squares in a row at the top.
          2. For each statement, draw a circle with its operator, with arrows from its input squares.
          3. Draw the result as a square below the circle, with an arrow from circle to square.
          4. If a result is used later (e.g. x1 used by y), draw an arrow from that square to the next circle.

            Remember: Round = Rules (operators) · Square = Stuff (values).

            Check yourself: in Fig 4.1, which operator must finish before z can be computed?

            The + that produces y (y = x1 + d), which itself needs the − producing x1.

            Lesson 5

            Reading a DFG: what can run in parallel or be reordered

            In plain words

            Follow the arrows. If two operators don't depend on each other (no path of arrows between them), they can run in any order or at the same time. In Fig 4.1, w = a+b, x1 = a−c and x2 = a+c all use only inputs, so they are independent. y must wait for x1, and z must wait for y.

            Why care? Processors have pipelines. If an instruction needs a result that isn't ready, the pipeline stalls. Placing an independent instruction in between hides the delay.

            Write this in the exam: advantages of DFG
            • It orders the way operations can be performed in a program.
            • It determines the feasible reorderings of operations, which reduces pipeline or cache conflicts.

            Remember: no arrow path between two operations means they are independent and can run in parallel.

            Check yourself: in Fig 4.1, is the order x2, w, x1, y, z valid?

            Yes. x2, w and x1 are independent; y comes after x1; z comes after y.

            Lesson 6

            CDFG: adding decisions to the picture

            In plain words

            Real programs have if, switch and loops. A CDFG handles them with two kinds of node:

            • Basic block nodes (rectangles): straight-line work ("do this").
            • Decision nodes (diamonds): a condition ("which way next?").

            Arrows leaving a diamond are labelled with the outcome: T / F for if and loops, or case values for switch. A CDFG is basically a flowchart with the rule "one box = one basic block".

            Write this in the exam
            • A CDFG constructs a model of both the decision flow and data flow of a program.
            • Data flow nodes are represented by basic blocks (sets of statements).
            • The control flow of a sequential program is represented by decision nodes.
            • Elements: basic block nodes, decision nodes, edges labelled with possible outcomes.

            Remember: the box does the work, the diamond decides, and every diamond edge gets a label.

            Check yourself: what goes on the arrows leaving a diamond for if (x > 0)?

            The labels T (true) and F (false), each leading to the block that runs in that case.

            Lesson 7

            if/else and switch in a CDFG

            In plain words

            if/else: one diamond with a T arrow to the "if" block and an F arrow to the "else" block. Both arrows then join into the next block. If there is no else, the F arrow goes straight to the next block.

            switch: one diamond with one arrow per case, labelled with the case value (c1, c2, c3, default).

            if (cond1) basic_block_1();
else       basic_block_2();
basic_block_3();
switch (test1) {
  case c1: basic_block_4(); break;
  case c2: basic_block_5(); break;
  case c3: basic_block_6(); break;
}

            Remember: if = two labelled arrows that merge again · switch = one arrow per case.

            Check yourself: how would if (a) f(); (no else) look?

            A diamond "a" with T → f() → next block, and F going straight to the next block.

            Lesson 8

            Loops in a CDFG: the back edge

            In plain words

              Lesson 1

              Why Petri nets exist

              In plain words

              In real systems many things happen at the same time and in unpredictable order. In a car park, one car arrives while another pays and a third leaves. That is concurrency. When processes don't follow a fixed schedule, and their start and order can change each run, they are asynchronous.

              A normal flowchart or state diagram shows one thing happening at a time. A Petri net can show many things happening together, things waiting for each other, and things competing for a shared resource.

              Write this in the exam
              • A Petri net is also called a Place/Transition net.
              • It is used for describing and analysing concurrent processes, and it is a graphical tool.
              • It is very similar to state transition diagrams that model system behaviour.
              • It is an abstract model showing the interaction between asynchronous processes, whose start and sequence may vary during execution.

              Remember: when a question says "graphical asynchronous modelling tool", it means a Petri net.

              Check yourself: what does "asynchronous" mean here?

              The processes don't run on a fixed common schedule. Their start and ordering can vary from run to run.

              Lesson 2

              The four parts: place, transition, arc, token

              In plain words

              Use a car park as the picture:

              • Place (circle) = a condition or waiting spot: "car waiting at gate", "free parking slots".
              • Transition (bar) = an event / action that changes things: "car parks".
              • Arc (arrow) = which places an event takes from and gives to. An arc always goes place → transition or transition → place, never place→place or transition→transition.
              • Token (black dot inside a place) = "this condition is true now" or "one unit of this resource is available". 3 dots in "free slots" = 3 free slots.
                Write this in the exam

                A Petri net has four components: places (circles), transitions (rectangles/bars), arcs (arrows) and tokens (black dots). Places represent possible states of the system. Transitions are events that change the state. Each arc connects a place with a transition or a transition with a place. A change of state is shown by tokens moving from place(s) to place(s).

                Remember: Please Take A Token · circle = condition, bar = event.

                Check yourself: can an arc join two places directly?

                No. Arcs always alternate: place → transition → place.

                Lesson 3

                How it moves: enabling, firing and marking

                In plain words

                The marking is a snapshot of how many tokens sit in every place. The starting snapshot is M0 (the initial marking). A transition is enabled (allowed to happen) only when every place with an arrow into it has at least one token. When an enabled transition fires:

                1. take one token from each input place,
                2. put one token into each output place.

                Example: p1 has 1 token and the net is p1 → t1 → p2. t1 is enabled; it fires; now p1 = 0 and p2 = 1. Tokens need not be conserved: a transition with 2 inputs and 1 output turns 2 tokens into 1.

                Markingp1p2t1 enabled?
                M010Yes
                M1 (after t1 fires)01No (p1 empty)
                Write this in the exam

                A change of state is caused by the firing of a transition; firing is the occurrence of an event. Firing depends on input conditions, shown by token availability. A transition is enabled when sufficient tokens are available in its input places. Once firing starts, tokens move from input to output places. (p1 = input place, p2 = output place.)

                Remember: all inputs have tokens → enabled → fire → take one from each input, give one to each output.

                Check yourself: t has inputs A (1 token) and B (0 tokens). Can t fire?

                No. Every input place needs a token, and B is empty.

                Lesson 4

                Properties 1 and 2: sequential execution and concurrency

                In plain words

                Sequential: p1 → t1 → p2 → t2 → p3. t2 can't happen until t1 has put a token in p2. The constraint is "t2 after t1", like "insert card, then enter PIN".

                Concurrency: one transition has two output places (a fork), so it creates two tokens. After that, t1 and t2 are independent and can fire in any order or together. Example: once a rover reaches a site, the camera and the sensors both start.

                Write this in the exam

                Sequential execution: t2 can take place only after t1, imposing the constraint "t2 after t1". Concurrency: t1 and t2 are concurrent processes; used in modelling distributed control systems.

                Remember: a chain means sequence; a split means concurrency.

                Check yourself: which construct models "the camera and GPS start together after power-on"?

                Concurrency: a fork where one transition outputs to two places.

                Lesson 5

                Properties 3 and 4: synchronization and merging

                In plain words

                Synchronization (join): a transition with two or more input places waits until all of them have a token. "A car can park only if a car is waiting AND a slot is free." This is the most useful construct in exam answers.

                Merging: several paths bring tokens to the same point. "Paid by card" and "paid by cash" both lead to "paid". Two transitions output into one place.

                Write this in the exam

                Merging: when several tokens arrive at the same transition, merging takes place. Synchronization: transition t1 is enabled only when at least one token is available at each of its input places.

                Remember: join = AND (wait for all) · merge = paths coming together.

                Check yourself: which construct is "data can be sent only when image AND sensor data AND link are ready"?

                Synchronization: a join transition with three input places.

                Lesson 6

                In plain words

                Conflict (choice): one place with one token feeds two transitions. Both are enabled, but firing one takes the token away, so only one happens. "PIN correct → approve" vs "PIN wrong → reject".

                Mutual exclusion: a shared resource place with one token (e.g. "kiosk free") feeds several transitions. Whoever takes the token uses the resource; the others wait until it is returned. This guarantees "one at a time".

                  Some drawings show what the system is made of (structure, like a floor plan). Others show how it behaves over time (behaviour, like a video of people using the house).

                  Structure diagrams (static)Behaviour diagrams (dynamic)

                  Write this in the exam
                  • A modelling language is a graphical/textual language that explains the design and construction of a model following a set of guidelines. Importance of modelling: visualization, reduced complexity, documentation.
                  • UML is a general-purpose visual modelling language used to visualize, specify, construct and document. Tools can generate code from UML diagrams. It is pictorial and works for software and non-software systems (e.g. process flow in automated systems). It is based on object-oriented analysis.
                  • Uses: forecast systems, estimate reusability, lower costs, plan and analyse behaviour, easier maintenance/modification.

                  Remember: UML does 4 things: Visualize, Specify, Construct, Document ("Very Smart Code Design").

                  Check yourself: is the use case diagram a structure or a behaviour diagram?

                  Behaviour. It shows how users interact with the system. The class diagram is the structure diagram in this unit.

                  Lesson 2

                  Use case diagram: the "menu card" of a system

                  In plain words

                  A use case diagram is like a restaurant's menu: it lists what you can get from the system, not how the kitchen cooks it. It answers: who uses the system, and what can each of them do?

                  Four ingredients: actors (who), use cases (what they can do), the system boundary (a rectangle separating inside from outside), and relationships (lines and arrows).

                  Write this in the exam
                  • The use case diagram shows the different ways a user can interact with the system, including interaction with people or external systems.
                  • It contains use cases and actors and depicts how actors interact with use cases.
                  • It describes the relationship between functionalities and their controllers.
                  • Components: actors, use cases, system, relationships.

                  Remember: WHO (actors) + WHAT (use cases) + a box (system) + lines (relationships).

                  Check yourself: does a use case diagram show the order in which things happen?

                  No. It only shows what functions exist and who uses them. Order in time belongs to sequence or activity diagrams.

                  Lesson 3

                  Actors and use cases

                  In plain words

                  An actor is a role outside the system that interacts with it, drawn as a stick figure. It can be a person (Student, Doctor) or another system (Bank, Billing System, SMS gateway).

                  • Primary actor: starts the interaction for their own goal (Customer). Draw on the left.
                  • Secondary actor: responds / helps (Bank, Billing System). Draw on the right.

                  A use case is one goal the actor can achieve, drawn as an ellipse inside the boundary and named Verb + Noun: "Register for Courses", "Pay Fee". Keep it high-level: "Book Appointment", not "Click the button".

                  Write this in the exam

                  A use case represents the high-level functionalities of a system and is drawn as an ellipse. An actor is an internal or external entity. The primary actor initiates the process; the secondary actor responds.

                  Remember: actors stay outside the box · primary on the left starts it · secondary on the right responds · use cases are Verb + Noun.

                  Check yourself: in "the registration system sends information to the billing system", what is the billing system?

                  A secondary actor (an external system), drawn on the right.

                  Lesson 4

                  Relationships 1: association, generalization, dependency

                  In plain words
                  • Association: a plain line from an actor to a use case, meaning "this actor takes part in this use case". Multiplicity (1, *) can show how many.
                  • Generalization: parent–child ("is a kind of"). Solid line with a hollow triangle at the parent. "New customer" and "Old customer" are kinds of Customer; "Pay from Savings" is a kind of "Make Payment".
                  • Dependency: a dashed arrow. The arrowhead points to the independent element; the tail end is the dependent one.
                  Write this in the exam

                  Association: relationship between two elements, describing how they are associated; can show multiplicity (1, *). Generalization: parent–child (inheritance) relationship, arrow with a hollow head. Dependency: dotted arrow; the arrowhead is the independent element, the other end is dependent.

                  Remember: plain line = participates · hollow triangle = is-a-kind-of (points to the parent).

                  Check yourself: which end gets the hollow triangle in "Pay by Card is a kind of Make Payment"?

                  The parent, "Make Payment".

                  Lesson 5

                  Relationships 2: «include» vs «extend», the most-tested idea

                  In plain words

                  Both are dashed arrows between two use cases. The difference is always vs sometimes:

                  • «include»: the base use case always calls the other one. "Log In" always "Verify Password". Arrow: base → included.
                  • «extend»: the extra use case happens only sometimes, under a condition, adding to the base. "Display Login Error" happens only if the password is wrong. Arrow: extension → base.

                  Test: ask "Can the base finish without it?" If never, it's include. If yes (it's optional), it's extend.

                  Remember: Include = Inevitable, points at the helper · Extend = Extra, points back home.

                  Check yourself: "During registration a student can request a course catalogue." Include or extend? Which way does the arrow go?

                    Lesson 9

                    Class relationships

                    In plain words
                    • Association (plain line): the classes know or use each other. Customer — Order.
                    • Aggregation (hollow diamond ◇ at the whole): "has-a", but the part can live on its own. A Department has Professors; close the department and the professors still exist.
                    • Composition (filled diamond ◆ at the whole): "made of". The part dies with the whole. Delete an Order and its OrderItems vanish.
                    • Inheritance / generalization (hollow triangle △ at the parent): "is-a". Customer is a User.
                    • Dependency (dashed arrow): temporarily uses, e.g. as a method parameter.
                    • Realization (dashed line + hollow triangle): a class implements an interface.

                      Remember: Hollow ◇ = Hangs around · Filled ◆ = Fatal. The diamond always touches the whole.

                      Check yourself: Rover and its mounted Sensors: aggregation or composition?

                      Composition (◆ at Rover). The sensors are physically part of that rover and have no life without it. (Aggregation is also accepted if you justify that sensors can be reused.)

                          State diagram: states and transitions

                          In plain words

                          A state is a condition an object stays in until something happens: a traffic light is Red, a phone is Locked, an ATM is Reading card. A transition is the arrow to the next state, triggered by an event. Write transition labels as:

                          event [guard] / action

                          e.g. insertCoin(v) [total ≥ price] / showReady(): when a coin is inserted, if the total is enough, do showReady and move on. Start with a filled circle (initial) and finish with a bullseye (final).

                            Write this in the exam
                            • A state diagram stores the status of an object and shows the condition of the system over a finite time. It is a behavioural diagram, also called a state machine / statechart.
                            • It explains the dynamic behaviour of a class and the reaction of objects to external stimuli.
                            • Uses: depict event-driven objects, show use cases in a business context, show the overall behaviour of a state machine, model dynamic behaviour.

                            Lesson 6

                            Self-transitions, composite states, and how to draw one

                            In plain words

                            A self-transition is an arrow that leaves a state and comes back to the same state. Something happens, but the status doesn't change: "insert another coin" while still Collecting Coins.

                            A composite state is a big state with smaller states inside. "Brewing" contains Heating → Grinding → Pouring. An arrow leaving the big box (e.g. "fault") applies from any sub-state.

                            Write this in the exam: steps to draw
                            1. Identify the initial and final states.
                            2. Identify the possible states the object can be in.
                            3. Label the events that trigger the transitions.

                            Slide examples to quote: Online order: Idle → send order request → Special or Normal order → order confirmation → Dispatch order → final, with an abnormal exit state. ATM: Reading card → (card read) Reading PIN → (PIN read) Choosing transaction → Performing transaction → Ejecting card; "cancel pressed" from each state goes to Ejecting card.

                            Lesson 7

                            Activity diagram: actions, decisions and merges

                            In plain words

                            An activity diagram is a smart flowchart. Start at a filled circle, go through actions (rounded boxes named with verbs: "Enter PIN"), follow arrows (control flow), and end at a bullseye. A decision diamond splits the flow; each outgoing arrow gets a guard such as [valid] / [invalid]. A merge diamond brings alternative paths back together.

                            Write this in the exam
                            • An activity diagram is a behavioural diagram showing control flow from start to finish, including decision paths. It can show sequential and concurrent processing.
                            • Uses: model workflow with activities, model the logic of an algorithm, show the workflow between users and system, understand functionality, investigate business requirements.
                            • Slide example (order management): start → customer sends order request → system confirms the order → [Yes] confirm order → condition check [Yes] → dispatch order → termination; [No] branches end the flow.

                            Remember: actions are verbs · every decision arrow gets a [guard] · merge brings paths back.

                            Check yourself: what is the difference between a decision node and a merge node? Both are diamonds.

                            A decision has one input and several guarded outputs; a merge has several inputs and one output.

                            Lesson 8

                            Parallel work (fork/join), swimlanes, and how to draw one

                            In plain words

                            A fork is a thick black bar that splits one flow into parallel flows, e.g. "update doctor schedule" and "send SMS" at the same time. A join is a thick bar that waits for all parallel flows to finish before continuing. Swimlanes are vertical columns (Patient | System | Doctor) that show who performs each action. The elevator slide uses lanes ELC (Elevator Logic Control) and ERS (Elevator Request Service).

                              Write this in the exam: steps to draw
                              1. Identify the initial and final states.
                              2. Identify the intermediate activities needed to go from initial to final.
                              3. Identify the conditions or constraints that change the control flow.
                              4. Draw the diagram with the proper notations.

                              Remember: fork splits into parallel paths · join waits for all · lanes show who does what.

                              5Tips & traps

                              Tip: Number every sequence message (1, 2, 3…) and write parameters in brackets. It looks professional and makes marking easy.
                              Tip: In activity diagrams, every decision diamond needs [guards] on all outgoing edges, and every fork needs a matching join.
                              Trap: State boxes named with verbs ("Insert coin") make it an activity diagram. Name states as conditions ("Collecting coins", "Idle").
                              Trap: Sequence diagrams have no decision diamonds. Use alt/opt frames.

                              Glossary

                              One-line definitions you can quote in a 2-mark answer. Filter by typing a term or a unit (e.g. "U5").

                              Host
                              U1
                              General-purpose computer where embedded software is written, built and debugged.
                              Target
                              U1
                              The embedded hardware the final binary image runs on; limited resources, no development tools.
                              Cross-compiler
                              U1
                              Runs on the host and generates machine code for a different target processor.
                              Native compiler
                              U1
                              Runs on and generates code for the same platform.
                              Preprocessor
                              U1
                              Separate step before compiling that handles #include, #define, conditional compilation, #line.
                              Object file
                              U1
                              Compiler output of op-codes + data in sections; not directly executable (COFF/ELF format).
                              COFF / ELF
                              U1
                              Common Object File Format / Executable and Linkable Format: standard object file structures.
                              .text / .data / .bss
                              U1
                              Code / initialized global variables / uninitialized global variables.
                              Linker
                              U1
                              Combines object files and libraries, resolves unresolved symbols, merges sections → relocatable program.
                              Relocatable program
                              U1
                              Complete program whose code and data have not yet been assigned memory addresses.
                              Locator
                              U1
                              Assigns physical addresses using the target memory map → executable binary image (built into GNU ld).
                              Linker script
                              U1
                              File giving ENTRY, MEMORY regions and SECTIONS placement to the linker/locator (-T option).
                              Map file
                              U1
                              Linker output listing final addresses and sizes of sections and public symbols (-Map option).
                              Binary image / hex code
                              U1
                              Final executable with physical addresses, ready to be downloaded to the target.
                              Startup code
                              U1
                              Runs before main(): sets up the stack, copies .data from ROM to RAM, zeroes .bss.
                              Interpreter
                              U1
                              Executes source line by line at run time; quick to iterate, slow and memory-hungry on an MCU.
                              Device programmer
                              U2
                              Hardware that burns the binary image into a chip placed in its socket, off the board.
                              ISP / ICSP
                              U2
                              In-system (in-circuit serial) programming: programs the chip while it stays installed on the board.
                              Bootloader / OTA
                              U2
                              Resident code that receives a new image over a comm link and rewrites flash, enabling remote updates.
                              Simulator
                              U2
                              Host program imitating the target instruction set; no peripherals; cheap; 100–1000× slower.
                              Remote debugger
                              U2
                              Host front-end + target back-end over a comm link; breakpoints, stepping, register/memory access.
                              ICE
                              U2
                              In-circuit emulator: hardware replacing the target CPU; debugs startup and ROM code; expensive.
                              Logic analyzer
                              U2
                              Captures many digital signals, converts them to 0/1 using a threshold, stores and displays them.
                              Timing analyzer
                              U2
                              Asynchronous logic analyzer mode that samples with its internal clock.
                              State analyzer
                              U2
                              Synchronous mode that samples on an external clock from the system under test.
                              SUT
                              U2
                              System Under Test: the digital circuit probed by the logic analyzer.
                              IDE
                              U2
                              Integrated Development Environment: editor, build tools and debugger in one GUI.
                              Code optimization
                              U3
                              Transformation that makes code faster/smaller/lower-power without changing its output.
                              Machine-independent
                              U3
                              Optimization ignoring target properties (folding, CSE, loop opts).
                              Machine-dependent
                              U3
                              Optimization using target properties such as registers and special instructions (peephole).
                              Constant folding
                              U3
                              Evaluating constant expressions at compile time (22/7 → 3.14).
                              Constant propagation
                              U3
                              Replacing a variable with its known constant value where it is used.
                              Algebraic simplification
                              U3
                              Using identities: i+0 = i, i*0 = 0, i−i = 0.
                              Strength reduction
                              U3
                              Replacing costly operators with cheaper ones (A*2 → A+A).
                              Dead code elimination
                              U3
                              Removing code that never runs or whose result is never used.
                              CSE
                              U3
                              Common sub-expression elimination: compute a repeated expression once and reuse it.
                              Code motion
                              U3
                              Moving loop-invariant computations outside the loop.
                              Induction variable
                              U3
                              Variable changing by a fixed step each iteration; multiply can become add.
                              Peephole optimization
                              U3
                              Machine-dependent improvement over a small window of 2–3 instructions.
                              Machine idiom
                              U3
                              Special target instruction replacing a general one (ADD #1,R → INC R).
                              Local / global optimization
                              U3
                              Within one basic block / across basic blocks using data-flow analysis.
                              Basic block
                              U4
                              Straight-line code with one entry and one exit, no branches inside.
                              Single assignment form
                              U4
                              Each variable is assigned only once; re-assignments are renamed (x1, x2).
                              DFG
                              U4
                              Data flow graph of a basic block: round operator nodes, square value nodes.
                              CDFG
                              U4
                              Control data flow graph: basic-block nodes + decision nodes with labelled edges; hierarchical.
                              Decision node
                              U4
                              Diamond in a CDFG representing a condition; edges labelled with outcomes.
                              Back edge
                              U4
                              Edge returning to an earlier node; represents a loop.
                              Petri net
                              U5
                              Place/transition net for modelling concurrent, asynchronous processes.
                              Place
                              U5
                              Circle representing a state or condition; holds tokens.
                              Transition
                              U5
                              Bar/rectangle representing an event that changes state.
                              Arc
                              U5
                              Arrow joining a place to a transition or a transition to a place.
                              Token
                              U5
                              Black dot marking a current condition or available resource.
                              Marking
                              U5
                              Distribution of tokens over all places; M0 is the initial marking.
                              Enabled / firing
                              U5
                              Enabled when all input places have tokens; firing moves tokens from inputs to outputs.
                              Synchronization
                              U5
                              Transition waits until each of its input places has a token (join).
                              Conflict
                              U5
                              Two transitions compete for the same token; only one fires.
                              UML
                              U6
                              Unified Modelling Language: visual language to visualize, specify, construct and document systems.
                              Actor
                              U6
                              External role (person or system) interacting with the system; primary initiates, secondary responds.
                              Use case
                              U6
                              Ellipse naming a high-level function the system provides to an actor.
                              «include»
                              U6
                              Base use case always invokes the included use case; arrow base → included.
                              «extend»
                              U6
                              Optional/conditional behaviour added to a base use case; arrow extension → base.
                              Generalization
                              U6
                              Inheritance (is-a) between actors, use cases or classes; hollow triangle at the parent.
                              Association
                              U6
                              Structural link between classes (or actor–use case) shown by a line.
                              Aggregation
                              U6
                              Weak whole–part (has-a); part can exist alone; hollow diamond at the whole.
                              Composition
                              U6
                              Strong whole–part; part dies with the whole; filled diamond at the whole.
                              Multiplicity
                              U6
                              How many objects take part in an association: 1, 0..1, 0..*, 1..*, m..n.
                              Visibility
                              U6
                              + public, − private, # protected, ~ package.
                              Lifeline
                              U7
                              Dashed vertical line below an object showing its existence over time.
                              Activation bar
                              U7
                              Thin rectangle on a lifeline showing when the object is executing.
                              Combined fragment
                              U7
                              Frame (alt, opt, loop, par) grouping messages with a condition.
                              State
                              U7
                              Condition of an object during which it waits for an event or performs an activity.
                              Guard
                              U7
                              Boolean condition in [brackets] that must be true for a transition or flow to happen.
                              Composite state
                              U7
                              State containing nested sub-states.
                              Fork / Join
                              U7
                              Thick bar splitting flow into parallel paths / waiting for all of them to finish.
                              Swimlane
                              U7
                              Partition in an activity diagram showing who performs each action.
